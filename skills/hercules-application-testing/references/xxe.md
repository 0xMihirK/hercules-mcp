# XML external entity handling

Use this playbook only for the named boundary in an authorized target or isolated fixture. Confirm target, identities, impact limits, and stopping condition before active work. Read saved notes and artifacts first; start the container only when a Docker-backed operation is actually needed.

## Hercules route

`network_curl` for exact XML media type/body; an owned callback only when explicitly permitted. Check the live MCP tool list and backend availability; raw shell and browser commands do not inherit structured target guarantees.

## Test sequence

1. Confirm the endpoint parses XML and compare a normal document with one harmless external-reference probe to an authorized fixture. Record parser diagnostics and callback contact without requesting local secrets. Distinguish DTD rejection from downstream entity resolution.
2. Positive control: Ordinary XML is accepted and parsed as documented.
3. Negative control: External references are disabled or confined and the callback sees zero contacts.

## Evidence and decision

Retain xML bodies, parser responses, callback logs, and validation state. Record what was observed separately from inferred impact. A valid control establishes that the test path worked; a missing result without that control is inconclusive.

## Limits and cleanup

A 500 or absent callback can reflect disabled networking rather than safe parsing; document the layer tested. Remove disposable records and markers only within the approved fixture, retain request/response artifacts, settle owned jobs, and stop the Hercules container after coordinated work.
