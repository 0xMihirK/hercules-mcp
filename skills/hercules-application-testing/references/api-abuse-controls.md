# API business abuse controls

Use this playbook only for the named boundary in an authorized target or isolated fixture. Confirm target, identities, impact limits, and stopping condition before active work. Read saved notes and artifacts first; start the container only when a Docker-backed operation is actually needed.

## Hercules route

`network_curl` for exact methods, bodies, and headers; `browser_*` only when browser state is required. Check the live MCP tool list and backend availability; raw shell and browser commands do not inherit structured target guarantees.

## Test sequence

1. Map the workflow's price, quota, or state transition before probing. Repeat one authorized transaction with a single controlled variation, such as order of calls or ownership, and compare ledger state rather than relying on status codes. Use disposable identities and restore their data.
2. Positive control: The authorized sequence produces the documented state change.
3. Negative control: An invalid sequence or different owner does not produce that change.

## Evidence and decision

Retain paired requests, timestamps, actor IDs, and resulting state or balance. Record what was observed separately from inferred impact. A valid control establishes that the test path worked; a missing result without that control is inconclusive.

## Limits and cleanup

Rate limiting or eventual consistency can hide effects; wait for a bounded reconciliation before concluding. Remove disposable records and markers only within the approved fixture, retain request/response artifacts, settle owned jobs, and stop the Hercules container after coordinated work.
