# Command-channel observability

Use this playbook only for the named boundary in an authorized target or isolated fixture. Confirm target, identities, impact limits, and stopping condition before active work. Read saved notes and artifacts first; start the container only when a Docker-backed operation is actually needed.

## Hercules route

`network_curl` or `ncat` for an owned local protocol fixture; `workspace_inspect` for traces. Check the live MCP tool list and backend availability; raw shell and browser commands do not inherit structured target guarantees.

## Test sequence

1. Define the sanctioned controller/agent pair, transport, heartbeat pattern, and observable controls. Send only inert fixture messages and compare expected versus unauthorized command sources. Verify termination and retained log coverage.
2. Positive control: Owned fixture channel exchanges one known harmless message.
3. Negative control: Unrecognized peer cannot command or read the fixture.

## Evidence and decision

Retain socket endpoints, message IDs without secrets, trace, and shutdown record. Record what was observed separately from inferred impact. A valid control establishes that the test path worked; a missing result without that control is inconclusive.

## Limits and cleanup

Do not deploy persistent remote-control software or route through public infrastructure without separate authorization. Remove only test-owned artifacts and processes through an approved path, verify the resulting state, retain evidence, and stop the Hercules container after coordinated work. Report cleanup uncertainty rather than claiming success.
